name: merge-request
description: Create a new merge request for the specified platform by the user
disable-model-invocation: true
argument-hint: "What CLI tool should I use for the MR?"
---

Create a merge request (pull request) for the current branch on the platform the user names, with a concise, short summary of the changes.

## 1. Resolve the provider

Treat the user's arguments as the provider. Map it to its CLI:

| Provider       | CLI   | Auth check                    | Create command                                                                    |
| -------------- | ----- | ----------------------------- | --------------------------------------------------------------------------------- |
| GitHub         | `gh`  | `gh auth status`              | `gh pr create --base <base> --head <branch> --title <title> --body <description>` |
| GitLab         | `glab`| `glab auth status`            | `glab mr create --target-branch <base> --source-branch <branch> --title <title> --description <description> --yes` |
| Azure DevOps   | `az`  | `az account show`             | `az repos pr create --target-branch <base> --source-branch <branch> --title <title> --description <description>` |
| Gitea/Forgejo  | `tea` | `tea login list`              | `tea pulls create --base <base> --head <branch> --title <title> --description <description>` |

If no argument was given, infer the provider from `git remote get-url origin` and confirm it with the user before continuing. If the provider isn't in the table, use its official CLI if one exists; otherwise go to the fallback in step 5.

## 2. Gather the changes

1. Get the current branch (`git branch --show-current`). If it is the default branch, stop and tell the user to create a feature branch first.
2. Find the base branch: use one the user named, else the remote's default branch (`git symbolic-ref refs/remotes/origin/HEAD`, or the provider CLI's repo view).
3. Read the changes with `git log --oneline <base>..HEAD` and `git diff <base>...HEAD --stat`, plus the full diff where you need it to understand intent.
4. If there are uncommitted changes, warn the user that they won't be in the MR. Don't commit them yourself.

## 3. Write the title and description

- **Title**: one line, imperative mood, under ~70 characters, saying what the change does (e.g. `Add tmux session picker keybind`). Follow the repo's existing conventions (e.g. Conventional Commits) if the log shows any.
- **Description**: short and concise. A one or two sentence summary of what changed and why, then a brief bullet list of the notable changes only if there is more than one. No filler, no restating the diff file by file, and no "generated by" footers.

## 4. Check the CLI and credentials

1. Check the CLI is installed with `command -v <cli>`. If it isn't, go to step 5.
2. Run the auth check from the table. If the user is logged in, use those credentials; don't ask for anything.
3. If the user isn't logged in, ask them how they want to authenticate. Prefer having them run the CLI's own interactive login themselves (e.g. `gh auth login`, `glab auth login`, `az login`). If they'd rather give you a token, have them export it in an environment variable the CLI reads (`GH_TOKEN`, `GITLAB_TOKEN`, `AZURE_DEVOPS_EXT_PAT`) instead of pasting it into the chat. Never echo, log, or write a token to disk.

## 5. Create the MR, or fall back

**If the CLI is installed and authenticated:**

1. If the branch has no upstream or has unpushed commits, push it with `git push -u origin <branch>`. Never force push and never push to the base branch.
2. Run the create command. Pass the description with a heredoc or a temporary file so newlines and quotes survive.
3. Report the MR URL the CLI returns.

**If the CLI isn't installed, the provider has no CLI, or creation fails**, print exactly this block and nothing else inside it:

```
TITLE: <MR Title>
DESCRIPTION: <MR Description>
```

After the block, explain in a sentence or two why the MR couldn't be created (e.g. "`glab` isn't installed; install it with `sudo dnf install glab` and run `glab auth login`, or create the MR manually with the title and description above."). If creation failed, include the CLI's error message.
